# LumeTrace Import and Migration Boundary

LumeTrace currently supports generic physical-folder initialization and LumeTrace backup restoration. It does not yet provide product-specific migration from Eagle or another application's private database.

## Create an empty file workspace

The create flow associates a user-selected physical root with a new workspace database and version-snapshot directory. The workspace starts without imported file records.

## Initialize from an existing folder

The existing-folder flow:

- recursively reads the selected physical folder while excluding hidden directories whose names begin with `.`;
- preserves the physical folder hierarchy and files in place;
- registers folders and files in the new workspace database;
- creates the initial version snapshot for each file;
- reports count and progress during the blocking initialization stage;
- queues readable-content extraction and optional semantic indexing as background work after registration.

It does not inspect or migrate Virelume, Eagle, or other application SQLite data. Search indexes and embeddings are generated by LumeTrace from the physical files.

## Restore a LumeTrace backup

Backup restore is different from generic folder initialization. A valid LumeTrace backup restores its files, Trash content, version records, and local indexes into the current workspace, using a newly created physical root under the selected destination. The previous physical root remains on disk, while the current workspace records and managed version store are replaced by the verified backup. Restore validates staged data and rolls back if replacement fails.

## Virelume extraction boundary

LumeTrace originated from Virelume's File Space, but it does not copy Virelume's Task, Cell, Continuum, Blueprint, Mem0/MemOS memory runtime, or multi-Agent orchestration model. LumeTrace's current Agent CLI integration belongs only to its file-space AI assistant.

## Future adapters

An Eagle importer or another application-specific adapter would need to define and verify:

- which physical assets and folder/group relationships are retained;
- how Tags and metadata map into LumeTrace;
- how duplicates and missing assets are handled;
- whether any source history can be represented honestly as LumeTrace versions;
- how extraction, FTS5, and semantic indexing are rebuilt after import.

Until such an adapter has a real tested path, one-click migration is not a current capability.
